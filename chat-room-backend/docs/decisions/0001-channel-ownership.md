# ADR 0001：频道所有权唯一事实来源

- 状态：已接受
- 日期：2026-07-30
- 范围：阶段 0 业务与数据基线

## 背景

当前模型同时用 `channels.creator_id` 和 `channel_members.role=CREATOR` 表示频道所有者。现有转让逻辑只修改成员角色，不更新 `creator_id`，因此两处数据会发生分歧。

## 决策

1. `channels.creator_id` 是频道所有权的唯一权威字段。
2. `channel_members.role=CREATOR` 暂时作为兼容镜像保留，不单独作为所有权鉴权依据。
3. 创建者判断统一使用 `channel.creator.id == currentUser.id`。
4. 管理权限由“权威创建者”或 `ADMIN` 成员获得；普通接口不得写入 `CREATOR`。
5. 所有权转让必须在同一事务中锁定频道并完成以下状态变化：
   - `channels.creator_id`：原创建者 → 目标成员；
   - 原创建者成员角色：`CREATOR` → `ADMIN`；
   - 目标成员角色：`MEMBER/ADMIN` → `CREATOR`。
6. 转让完成后必须满足：
   - `creator_id` 对应用户仍是频道成员；
   - 该成员的镜像角色为 `CREATOR`；
   - 频道中恰好有一个 `CREATOR` 镜像。

## 权限矩阵

| 操作 | CREATOR | ADMIN | MEMBER |
|---|---:|---:|---:|
| 修改频道、禁言、邀请成员 | 允许 | 允许 | 禁止 |
| 踢出普通成员 | 允许 | 允许 | 禁止 |
| 踢出管理员 | 允许 | 禁止 | 禁止 |
| 提升或降级管理员 | 允许 | 禁止 | 禁止 |
| 转让或解散频道 | 允许 | 禁止 | 禁止 |

## 既有数据的迁移规则

阶段 0 审计发现频道 `20` 和 `23` 存在唯一 `CREATOR` 镜像与 `creator_id` 不一致。由于旧代码的转让操作只更新成员角色，这两个唯一镜像代表用户实际执行过的转让意图。后续版本化迁移应：

1. 将 `creator_id` 更新为当前唯一 `CREATOR` 镜像用户；
2. 将旧 `creator_id` 对应成员调整为 `ADMIN`；
3. 再校验每个频道只有一个 `CREATOR` 镜像。

阶段 0 只记录迁移输入，不直接修改业务数据。

## 后续实现约束

- 转让读取频道时使用数据库行锁或等价并发控制。
- 删除频道、退出频道、转让、提升与降级均调用同一套所有权判断。
- 角色更新通用接口不得成为写入 `CREATOR` 的旁路。
- 数据修复必须通过版本化迁移执行，不直接运行当前 `schema.sql`。
